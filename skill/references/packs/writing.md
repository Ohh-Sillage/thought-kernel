# 场景包：写作创作（`writing`）

## 1. id 与语义标签

`writing` —— 从零产出一份文字成品：邮件、文章、讲稿、报告、文案、纪要。

## 2. 适用信号

用户要的产物是**一段能直接发出去的文字**：

- 「帮我写 / 起草 / 润色 / 改成 XX 语气 / 写个邮件 / 写篇稿子」；
- 给了要点、素材或上文，等的是成文而不是建议；
- 「这份文档该怎么写」但上下文明显是让他出稿。

判据：**产物能不能被复制粘贴出去用**。能 → 本场景。

## 3. 不适用信号

| 易混场景 | 凭什么排除它不属于本场景 |
|---|---|
| `review` | 对象是**已经存在的文本或已发生的事**，要的是评价与改进项（「这段写得怎么样」「这次活动复盘」）。要新文本 → 本场景；要判断 → `review` |
| `exec`（兜底） | 只是**换格式**（转成表格、改成要点、翻成英文），不是从零写 |
| `planning` | 要的是**推进安排**，文字只是载体（周报里的下一步计划属于本场景，但「下周怎么排」属于 `planning`） |
| `learning` | 要的是**搞懂**某个概念，不是产出文案 |
| `coding` | 产物是代码或脚本，注释和文档只是附件 |

**边界提醒**：「写个周报」既可能是 `writing`（把已有工作写成文）也可能是 `review`（复盘得失）。
判据：**他有没有要你评价**。要评价得失 → `review`；只要成文 → 本场景。

## 4. 默认交付形态

**可直接使用的成文成品。** 不是大纲、不是要素清单、不是「该写什么」的指引。

- 邮件 → 完整邮件正文（含称呼、正文、落款），能直接粘进邮箱；
- 文章 / 稿子 → 完整段落，不是小标题骨架；
- 报告 / 文档 → 全文，包括开头的结论与结尾的行动项。

**篇幅按体裁定**：邮件可以短，但不能缺要素；报告可以长，但不能是目录。

## 5. 注入内容

**沿用通用三档装配，本包不额外覆盖额度。**（条数以 `@references/modes.md` 与 `@references/difficulty.md` 为准。）

一条本场景专属的优先级：

> **「交成文」优先于「交结构」。** 篇幅紧张时先删对结构的解释，不删正文本身。

## 6. 硬约束

1. **必须是成品，不是骨架。** 只有小标题 + 「此处展开」的，算未完成。
   实测依据：写作题里唯一交出完整成稿的那份得分最高；把「写邮件」做成要素清单的版本，
   配对差 **−3.33**（超噪声 5 倍）——这是全项目最大的一次单题失分。
2. **要素齐全**：按文体该有的都齐（邮件有称呼/事由/请求/落款；报告有结论/依据/行动项；
   讲稿有开场/主体/收束）。**短不等于缺**，但缺要素就是缺。
3. **主体与身份一律不许「示例」。** 这一条没有例外，是本节最硬的一条。

   | 对象 | 允许的做法 |
   |---|---|
   | **项目主体**（这是什么项目、给谁做的、什么业务域） | **只能二选一**：① 从用户给的素材 / 上文里取；② 用 `<占位>`。**不许编一个示例主体** |
   | **身份与角色**（公司、岗位、职级、团队规模） | 同上：取自素材，或占位 |
   | 结构、句式、篇幅口径、通行写法 | 可以直接给（这是「怎么写」的知识，不是「他做了什么」） |
   | 具体数字（业绩、指标、时间） | 可以给示例值，但**必须逐处标**「〔示例〕」，且集中列进替换清单 |

   **为什么「示例主体」比留空更糟**：一份 `〔业务域〕〔系统名〕` 的骨架，用户一眼就知道要填；
   而一份写着「企业知识库智能问答系统 · 客服 · 5 人 · 日均 4000 次」的**通顺成稿**，
   读起来像事实，用户读到第二段才发现这与自己毫无关系，整篇作废。

   实测（v1.5.0）：这条被理解成「主体也可以给示例」后，一份简历文案被写成了
   「企业知识库智能问答系统」，用户真实项目（个人站 / 简历生成）一个字都没用上——
   两位评委都判「只能整段重写」，一篇比空模板还低 4 分。
4. **用户给的事实必须原样用**（数字、名称、时间、结论），不得为了行文顺畅改动或「优化」它们。

## 7. 失效边界

- **「不得编造」不能被执行成「交空模板」**。T26 实测：因为怕编造，交出一份
  `〔业务域〕〔系统名〕〔指标〕` 的填空骨架，比裸模型给（带示例数字的）成稿低 4 分。
  正确做法是字段 6 第 3 条：**主体占位、其余写实**。（占位边界的通用规则见 `SKILL.md`「假设标注」。）
- **不要先问三个问题再写**。写作题的输入通常已经够写一稿；缺什么就在稿里用占位标出来，
  让用户看到成品后再改，比先做需求澄清快得多。除非缺的是「写给谁、什么目的」这种决定文体的事。
- 用户只给了标题、要求「写个提纲」时，交付形态是提纲（他要的就是结构），不要硬凑成文。
- 用户要求「润色/改写」时，交付形态是**改后的文本 + 改动说明**，不是分析原文哪里不好。

## 8. 自检项

- 是成文，能被直接复制粘贴出去用。
- 按文体该有的要素齐全，没有缺块。
- 用户的核心事实原样保留，没有被「优化」掉。
- **主体与身份取自用户素材或占位，没有被我编成「示例主体」**（结构/写法可以给示例，主体不行）。
- 数字类示例值已逐处标「〔示例〕」并列入替换清单。
- 篇幅与文体匹配（没有把邮件写成报告）。
- 末尾没有自我点评段落（「以上就是我写的邮件，你可以…」）。
