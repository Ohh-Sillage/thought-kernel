# 场景包：调试排错（`debugging`）

## 1. id 与语义标签

`debugging` —— 已有东西坏了：定位原因并修好。

## 2. 适用信号

用户带着**故障现象**来，要的是「为什么会这样 + 怎么修好」：

- 有报错信息、堆栈、日志、崩溃、蓝屏、闪退、超时、内存泄漏、偶发失败；
- 说「不工作了」「起不来」「卡住了」「一直闪」「无效」，且有一个**具体的不正常现象**；
- 贴了日志或配置，等的是判断，不是新功能。

判据：**有没有一个「本不该这样」的现象**。有 → 本场景。

## 3. 不适用信号

| 易混场景 | 凭什么排除它不属于本场景 |
|---|---|
| `coding` | 没有故障，用户要的是**新增能力**（「再帮我加个 X」「能不能支持 Y」）。功能缺失不是故障 |
| `exec`（兜底） | 一个是非查询（「这个端口被谁占用了」「X 命令怎么写」），没有「不正常的现象」 |
| `refactor` | 能跑但结构差 / 慢但符合预期，用户要的是改结构。性能**不达预期**算故障，结构**不好看**不算 |
| `review` | 要复盘的是**已发生的事**（上线出了什么问题、这个项目做得怎么样），范围大于单个故障 |
| `decision` | 在选型（「A 方案还是 B 方案」），不是某个东西坏了 |

**边界提醒**：一句话里既有报错又在问「该怎么设计」时，看**有没有一个必须修掉的现象**——有就先修，修完再谈设计。

## 4. 默认交付形态

**先给修复路径，再给根因候选。** 不是「排查框架」、不是「你这可能有几种原因」的清单。

顺序很重要：用户要的是修好，不是理解。

## 5. 注入内容

**不注入思考框架。** 用字段 6 的契约替代。

| 项 | 规则 |
|---|---|
| 人类侧思想（`H*`） | 不自动附加；用户显式点名时才附加 |
| 机器侧思想（`M*`） | 最多 1 条，且只允许 `M10`（反馈控制）做交付前自查 |
| 场景数 | 只取 top-1 |

> 为什么：实测带框架后 debugging 从 19.75 降到 16.50，三份输出把篇幅全给了「候选根因 + 可证伪验证」，
> **全都漏掉止损手段**——框架挤掉了交付要素。

## 6. 硬约束

### 先判适用性（这一步决定后面几项是必交还是可省）

| 条件 | 是否必需 1（止损）与 3（现场保留） |
|---|---|
| 影响**生产环境**或线上用户 | **必需** |
| 有**他人受影响**（同事、客户、下游系统） | **必需** |
| 后果**不可逆**（数据丢失、资金、对外发布） | **必需** |
| 三者都不成立（个人电脑的小毛病、本地脚本报错、单机配置问题） | **不列为必交项** |

**三者都不成立时**：直接给修复路径——先给「怎么修好」（命令 / 操作步骤 / 验证方法），
再补一句「如果修不好，再按下面的根因排查」。
**不要**对这类问题先讲梯度止损、导出注册表、保留现场——那是给用户加作业，不是帮他修好。

### 先分两种请求（这一步决定第 0 项写什么）

| 用户在说 | 交付顺序 |
|---|---|
| **「帮我修好」**（「一直闪」「起不来」「怎么弄」「咋整」+ 一个具体故障现象） | **修法优先**：第一段就是最可能的那个修法 |
| **「帮我判断」**（贴了日志 / 监控 / 数据，问「有没有问题」「正常吗」「是不是泄漏」） | **结论优先**：第一段是一句判断（正常 / 偏高 / 异常 + 依据的那个数），修法与操作在后 |

**判断错了顺序，后面写得再全也不算完成。** 把判断题写成操作指南，等于让用户在对结论还没把握时先动手。

### 四项（按此顺序，第 1 项是主件，其余按需）

0. **第一段必须给结论或修法**（按上表选其一）——
   - 「帮我修好」→ 一句话点名最可能的原因 + 对应的那条命令或操作；
   - 「帮我判断」→ 一句话说清「正常 / 偏高 / 异常」+ 支撑这个判断的具体数字。
   判据：用户只看第一段，就知道「该不该动手、先动哪个」。
   **不要用流程、清单、排查框架开头。这一步做错，后面补得再全也不算完成。**
   若结论依赖对数据的解读（百分比口径、单位、采样时点），**先用一句校准这个口径**再说结论——
   但校准也只能是一句，不能变成一节。

### 第一步怎么选：按「命中率 × 代价」，不按「机制解释力」

**这是本包最容易错的一步。** 模型天然会挑「机制讲得漂亮」的那个原因排第一，而用户要的是「最快不疼地试出一个结果」。

排序看三件事，顺序不能颠倒：

| 优先 | 判据 | 反例（不该排第一） |
|---|---|---|
| 1 **可逆** | 做错了能不能撤回，代价多大 | 删注册表值、清缓存、重置配置、重建索引、重装 |
| 2 **便宜** | 10 秒还是 20 分钟；要不要重启、要不要装东西 | 需要改系统设置 + 注销重进的 |
| 3 **不破坏证据** | 做完之后，原来的现象还能不能观察到 | 清缓存 → 重置顺序，「哪个先犯」这条线索就没了 |
| 4 命中率高 | 平台上最常见的那 1—2 个原因 | 见下方测试 |

**操作测试（用它自查第一条够不够格）**：
> 如果你能一句话讲清某个原因的机制，但**说不出它有多常见**，那它还没资格排第一。
> 反过来，如果一个 10 秒可逆的动作能区分两个大类原因，它必须排在任何破坏性动作之前——
> 哪怕后面那个原因的机制解释得更漂亮。

**现象里的不对称先用完**：用户的描述里常有「只有 X 出现 / A 正常 B 不正常 / 重启后好一阵又犯」。
这类差值是**最便宜的定位线索**，通常直接排除掉一半候选。先把它的含义讲清，再动手。

**要二分就一次只改一个变量**：需要「逐个关掉看还犯不犯」时，**一次只关一个**。
一次关两个，当场就把「是哪一个」的区分度丢了——省下的时间要用在后面重新逐个试回来。
同理：一次只改一项设置、一次只更新一个组件、一次只换一个观察口径。
如果确实要一次动多个（时间紧、风险低），必须明说「这一步放弃了定位，只看能否消失」。

**「一次一步」不等于「只交付一步」**：说清了执行顺序，后续步骤仍必须**全部写出来**——
命令、路径、备份方式、回滚方式，一样不能少。
**禁止**出现「真要走到那步再单独说」「后面按需再补」「到时我再给」这类把动作悬空的写法。
判据：**用户照这一份答案从头做到尾，中间不需要回来再问一次。**
实测（v1.4.4）：「先只退微信」这一条被写对了，代价是把注册表分支和 explorer 重启推给了「再单独说」，
两位评委都判「硬伤是断头」——**守住了纪律，丢了交付**。

**给折算值时，当场用另一个口径反算一遍**：同一段里出现两种表达（百分比 / 个数 / GB / 倍数）时，
它们必须互相验算一致。例：`114%` 在一台 12 核机器上 → 既可以说「1.14 个核」，也可以说「整机 9.5%」，
但**不能同时写 9.5% 又写「0.95 个核」**——这两个数互相矛盾，读者会照错的那个做。

1. **止损手段**（仅上表成立时必需）——灰度发布 / 回滚 / 限流 / 降级中至少一项，
   说明怎么用、代价是什么。没有止损手段的诊断结论不算完成。
   **上表三条件都不成立时，本项不写**——不要为了「齐全」而给个人电脑问题加止损段落。
2. **可证伪的验证判据**——**只给你实际在权衡的 2—3 条候选**，不要穷举。
   每条给出「什么现象出现说明它是」「什么现象出现说明它不是」。
   多于 3 条说明你还没收敛，先自己排除掉。
3. **现场保留**（仅上表成立时必需）——重启、改配置、清缓存之前，先说明要取哪些证据
   （日志、堆快照、线程栈、监控快照）。若某一步本身有破坏性（删注册表键、清缓存），
   **在该步内嵌一句备份动作即可**，不单列成节。
4. **根因候选排序**——按可能性排序，≤3 条，每条附「一句话怎么验证」。
   不写「也许 / 可能还有」这类穷举项。

### 判据必须双向且不等价

第 2 项的两列**不得互为否定式改写**（「有 X 则成立 / 无 X 则不成立」算同一条），
排除判据必须写出一个**具体的、可能被真实观察到的反例现象**，而不是「未观察到 X」。
实测中有输出把两列写成同一内容，形式上满足契约、实质是空壳。

### 执行详细程度按难度分档

| 难度 | 执行方式 |
|---|---|
| 简单 | 只交修复路径 + 第 4 项（一句话排序） |
| 中等 | 修复路径 + 四项（不适用时可省，省了要说明为什么可省） |
| 复杂 | 四项全交，且第 2 项每条候选都要双向判据 |

## 7. 失效边界

- **注入思考框架是负收益**，与难度无关。
- **把高风险排障的仪式套到日常小故障上是净伤害**：实测「托盘图标一直闪」这类个人电脑问题，
  先讲止损 + 导出注册表保留现场，会让用户拿不到「现在怎么修」，评分 −5。
- **把四项并列成清单，等于换一种形式复现上面那条毛病**。实测（v1.4.0 首版）：
  要求「四项齐全」的版本，「托盘图标闪」与「隐藏图标整排闪」两题在两位评委手里都掉 2—4 分，
  判词是「偏通用排查（msconfig 全禁、sfc/DISM），完全没提那个 Win10 主因」。
  所以第 0 项（最可能的修法）优先于一切完整性要求。
- 现象描述不足以定位（只有「不工作了」四个字、没有环境与复现步骤）时：
  给出**最可能的两三条路径 + 一条能立刻缩小范围的自查命令**，不要只反问。
- 用户已经在做破坏性操作（重置系统、删库）时，先喊停并说明代价，再给路径。
- 用户上文里试过某个办法（「我已经禁用了一遍」）时，**先解释它为什么没用**，再给下一步——
  不回答这一句，用户会以为你没看他的上文。
- **第一条是破坏性动作（删值 / 清缓存 / 重置 / 重建 / 重装）时，一定排错了**：
  即使它确实是命中率最高的原因，前面也必须先有一个可逆的隔离步骤。
  实测（v1.4.1）：把「清托盘图标缓存 + 删两个注册表值」放在第一步，两位评委一个判「定位准」、
  一个判「一上来就毁掉『哪个图标先闪』这条唯一定位线索」，分数分裂在 15 与 19 之间——
  **凡是要靠「评委怎么看」才能定优劣的写法，都不该出现在第一步**。

## 8. 自检项

- **第一段是修法或结论**（按「先分两种请求」那节选），不是流程、不是「先做准备工作」、不是候选清单。
- 判断题里，第一段的结论有具体数字支撑，且已校准口径（百分比、单位、采样时点）。
- **第一步可逆、便宜、不破坏证据**；若它不可逆，前面必须已有一个可逆的隔离步骤。
- 第一条修法说得清「有多常见」，而不只是「机制是什么」。
- 现象里的不对称（只有 X / A 正常 B 不正常）已经用上了，不是放着不管直接给方案。
- 二分定位时**一次只改一个变量**；一次动多个时已明说「这一步放弃了定位」。
- **后续步骤全都给了实体**（命令 / 路径 / 备份 / 回滚），没有「再单独说」「按需再补」这类悬空表述；
  用户照这一份做到尾不需要再回来问。
- 同一段里的两种口径（% / 个数 / GB）互相验算过，没有自相矛盾的折算。
- 有「先修什么」的明确第一步，不是纯分析。
- 每一步说清**怎么知道这一步成功了**。
- 排序 ≤3 条且有依据，不是「可能 / 也许」的穷举。
- 双向判据两列内容不同（不是否定式改写）。
- 高风险场景有止损；低风险场景**没有**多余的止损与取证作业。
- 用户上文提过已试过的办法，已回答「为什么没用」。
- 没有把用户没给的环境、版本、配置当成既定事实写进结论。
