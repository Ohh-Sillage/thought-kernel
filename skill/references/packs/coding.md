# 场景包：开发功能（`coding`）

## 1. id 与语义标签

`coding` —— 新增能力：写出原本不存在的代码、脚本、工具、接口、页面。

## 2. 适用信号

用户要的产物是**能跑起来的东西**：

- 明确要「写一个 X」「实现 Y 功能」「做个 Z 工具 / 页面 / 接口 / 脚本」；
- 给了一段需求和约束，等的是代码而不是方案；
- 问「这段怎么写」「有没有现成的实现」，并且准备直接拿去用。

判据只有一条：**交付物能不能被运行或安装**。能 → 本场景。

## 3. 不适用信号

| 易混场景 | 凭什么排除它不属于本场景 |
|---|---|
| `refactor` | 代码**已经能跑**，用户要的是改结构、去重复、提性能，且**外部行为不变**。有「重构 / 简化 / 拆 / 优化 / 解耦」且对象是现有代码 → 走 `refactor` |
| `debugging` | 有**故障现象**（报错、崩溃、不工作、偶发、超时）。用户要的是「它为什么不工作」，不是「给我加个能力」 |
| `planning` | 要的是**方案 / 架构 / 排期 / 取舍**，没有要求产出代码。出现「设计一下」「方案」「路线图」且用户没要可跑的东西 → 走 `planning` |
| `exec`（兜底） | 只要一条命令、一段配置、一句解释，产物是一行字而不是一个可运行单元 |
| `writing` | 产物是文字成品（文档、邮件、文案），代码只是附件或例子 |

**边界提醒**：一句话里同时出现「方案」和「实现」时，看**用户下一步要拿什么**——要拿去做决策选型走 `planning`，要拿去跑走本场景。

## 4. 默认交付形态

**可运行代码 + 一条能复现的运行命令。** 不是分层设计图、不是伪代码、不是「建议你按这个结构写」。

## 5. 注入内容

**不注入思考框架（分治 / 剪枝 / 状态抽象 / 奥卡姆剃刀等一律不注入）。** 用字段 6 的交付契约替代。

| 项 | 规则 |
|---|---|
| 人类侧思想（`H*`） | 不自动附加；用户显式点名时才附加 |
| 机器侧思想（`M*`） | 最多 1 条，且只允许 `M10`（反馈控制）做交付前自查 |
| 场景数 | 只取 top-1，不做多场景合并 |

> 为什么：本场景的价值判据是「能不能立刻用」，不是「思考过程是否完整」。思考框架在这里是纯成本——
> 占篇幅、改结构，却不提升交付物可用性。实测注入后 coding 从 18.25 降到 15.00，落差全在
> 「缺可运行入口与依赖安装说明」——框架挤掉了交付要素。

## 6. 硬约束（必交四项，缺一项即算未完成）

1. **可运行入口**——完整代码，或明确指出改哪个文件的哪一段；不能只有伪代码或架构描述。
2. **依赖与运行命令**——什么语言、什么库、怎么装、怎么跑，一条命令能复现。
3. **关键边界处理**——空输入、文件不存在、格式错误、权限不足中，与本题相关的那些必须有明确处理，不得裸抛异常。
4. **已知限制**——没实现的部分、做了哪些假设、在什么条件下会失效，显式写出来。

**执行详细程度按难度分档**（难度由主干按 `@references/difficulty.md` 判定后传入）：

| 难度 | 执行方式 |
|---|---|
| 简单 | 只交 1、2 两项，边界与限制一句话带过 |
| 中等 | 四项全交，每项 1—2 句 |
| 复杂 | 四项全交，且边界处理与已知限制**逐条列举** |

**优先级**：交付契约优先于思考过程。篇幅紧张时先删思考过程，不删上述四项。

## 7. 失效边界

- **注入任何思考框架都是负收益**，与难度无关：连复杂题也是裸模型更优。所以本包的字段 5 固定为「不注入」。
- 但**不等于零注入就最好**：实测完全不注入会让输出退回「只有设计、函数未定义的骨架」，独立评委实跑后只给 15—16 分。所以字段 6 的四项不能省。
- 用户只要一段解释、不要代码时，不属于本场景（见字段 3）。
- 需求里关键参数全缺（只有一句话、不知语言与环境）时，**先列假设再动手**，不要静默选一套技术栈——但不要因此把成品换成问卷。

## 8. 自检项

- 入口可定位：说清了代码在哪、从哪个文件开始跑。
- 运行命令可复现：一条命令 + 依赖安装，不需要用户猜。
- 边界已处理：本题相关的异常路径有明确分支，不裸抛。
- 限制已披露：未实现项、假设项、失效条件都写了。
- **没有虚报**：声称支持的参数、开关、输出格式，代码里都有对应实现（未被实际执行验证过的，标「未测试」并说明原因）。
