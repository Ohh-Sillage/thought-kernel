# 场景包：重构优化（`refactor`）

## 1. id 与语义标签

`refactor` —— 改结构不动行为：已有能跑的代码/文档/流程，去重复、降复杂度、提性能。

## 2. 适用信号

用户要的产物是**改过的结构 + 行为没变的证据**：

- 「重构 / 简化 / 拆一下 / 解耦 / 去重复 / 优化性能」且对象是**已经能跑的东西**；
- 说了「别改行为」「功能不变」，或者要的只是「结构更清楚」；
- 抱怨「太乱 / 嵌套太深 / 循环依赖 / 一个函数两百行」。

判据：**现有东西是能用的，用户嫌它不好**。→ 本场景。

## 3. 不适用信号

| 易混场景 | 凭什么排除它不属于本场景 |
|---|---|
| `coding` | 要**新增能力**，现有东西还不存在或不够用。有「加个功能 / 实现 X」→ `coding` |
| `debugging` | 有**故障现象**（报错、崩溃、不工作）。性能**不达预期**算故障，结构**不好看**不算 |
| `planning` | 要的是**先给方案再动手**（「你觉得该怎么拆」），且没要求产出改动 |
| `exec`（兜底） | 只是要一条建议或一次代码审查意见，不要求改 |

**边界提醒**：一句话里同时有「重构」和「加个功能」时，**先做哪一个**由用户定；
不要自己把两件事合成一次改动——行为变更与结构调整混在一起，出问题无法归因。

## 4. 默认交付形态

**改后的结构 + 行为不变的证据。** 不是「重构建议清单」，也不是只有新架构图。

- 代码 → 改后的代码（或明确的 diff 位置）+ 怎么验证行为没变（跑哪些测试、对哪些输入输出）；
- 文档/流程 → 新结构 + 与旧版的对照（哪几块合并了、删了什么、为什么能删）。

## 5. 注入内容

**沿用通用三档装配，本包不额外覆盖额度。**（条数以 `@references/modes.md` 与 `@references/difficulty.md` 为准。）

一条本场景专属的优先级：

> **「不编数字」优先于「显得专业」。** 见字段 6 第 1 条。

## 6. 硬约束

1. **三类数字必须分开处理**（本场景是全项目踩坑最多的地方）：
   - **通用经验阈值**（「圈复杂度 >15 需拆」「参数 >4 个」「覆盖 <60%」）→ **直接给，不要占位**。
     这类是行业经验值，占位反而让人没法用。
   - **用户特定数据**（团队人数、实际 QPS、既有代码行数、具体日期）→ 用 `<占位>` 并标注。
   - **无来源的量化断言**（「拆分能降低 3%—8% 开销」「0 风险」「1 小时能改完」）→ **不要编**。
     改成定性表述（「通常会多一层调用开销」）或标「需实测」。

   实测依据：`refactor` 曾因第 1 类也占位而 usability 全线被扣；
   也因第 3 类乱编而被判 fab（「3%—8% 开销」无来源、「0 风险 / 1 小时」工期承诺）。
   按三类分开处理后，`refactor` 从 **−1.50 修到 +1.83**。

2. **必须给「行为不变」的验证方式**：跑哪些测试、对哪几组输入比较输出、或者手工核对哪几处。
   **没有验证方式的重构等于提议，不算交付。**

3. **不许给工时承诺。** 评委原话：「在完全不知道代码形态时给出工时承诺，**比留白更糟**。」
   要说规模，用相对量（「改 3 个文件、约 5 处调用」），不用绝对时间。

4. **拆分要给边界**：新模块之间靠什么通信、共享状态放哪、为什么这条线切在这里。
   只给「拆成 A/B/C 三个模块」而不说边界的，是把问题原样搬了个地方。

## 7. 失效边界

- **不要为了「结构漂亮」而改**。用户没抱怨、也没有实际代价（难改、慢、易错）的地方，不要动。
- **一次只改一类问题**。同时去重复 + 改命名 + 调依赖方向，一旦出问题无法定位是哪一步导致的。
- 用户只要「看看有什么问题」时，交付形态是**问题清单 + 优先级**，不是直接给改后的代码。
- 性能优化必须先要**基线数字**。没有基线就说「优化了 X%」是编的（见字段 6 第 1 条第 3 类）。

## 8. 自检项

- 改的是结构，行为描述没变（或明确标出唯一的行为变更点并单独说明）。
- 给了「行为不变」的验证方式。
- 三类数字分开处理了：通用阈值直接给、用户数据占位、无来源断言不编。
- 没有工时承诺；规模用相对量描述。
- 拆分有边界说明，不是只给模块名。
- 只改了一类问题，没有把命名/结构/依赖混在一次改动里。
