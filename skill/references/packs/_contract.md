# 场景包契约（新增/修改任何场景包前必读）

本目录下每个 `<id>.md` 是**一个场景的完整封装**。主干只认下面 8 个字段，不认字段之外的内容。

## 一、8 个字段（顺序固定，标题格式固定）

```markdown
# 场景包：<中文名>（`<id>`）

## 1. id 与语义标签
## 2. 适用信号
## 3. 不适用信号
## 4. 默认交付形态
## 5. 注入内容
## 6. 硬约束
## 7. 失效边界
## 8. 自检项
```

| # | 字段 | 必须回答的问题 | 不合格的样子 |
|---|---|---|---|
| 1 | id 与语义标签 | 稳定标识是什么、一句话是什么任务 | 用中文名当主键 |
| 2 | 适用信号 | 用户要什么**产物** → 属于本场景 | 写成关键词罗列（那是判定引擎的实现细节） |
| 3 | **不适用信号** | 和谁易混、凭什么排除 | **缺这一项就违规**——场景之间会靠排序抢，边界抖动 |
| 4 | 默认交付形态 | 成文 / 可跑代码 / 判断 / 清单 / 时间表 / 解释 | 让主干去猜 |
| 5 | 注入内容 | 允许注入的 1—N 条（按 id 引用 `@references/thoughts.md`），以及「不注入」时的替代 | 把模板全文内联 |
| 6 | 硬约束 | 本场景**必交项**，缺一项即算未完成 | 写在主干里（这正是要消灭的毛病） |
| 7 | 失效边界 | 什么情况下**注入是负收益** → 只按字段 4、6 交付 | 不写 → 无法解释为什么本场景要豁免 |
| 8 | 自检项 | 交付前的场景级检查（只查本场景特有项，通用项见主干） | 与主干通用自检重复 |

## 二、三个「不许」

1. **主干不许引用场景名**：`SKILL.md` 的闸门 / 模式 / 装配 / 输出协议 / 兜底 / 诚实性 / 自检各节，
   不得出现任何 `<id>` 字面。主干只通过 `@references/scenario-map.md` 的「包索引」按 id 取文件。
2. **场景包不许互相引用**：不得写「见 xxx 包」。需要共享的内容**上提到主干或模板库，或各自复制一份**——
   宁可重复，不要耦合。
3. **场景包不许修改装配规则**：包只能声明自己的**额度需求**（注入几条、要不要 top-1），
   不能改「按模式 × 难度裁剪」这条通用规则本身。
4. **单包体量：超过主干正文的 1/2 要能说出理由，不得达到或超过主干本身。**
   包是给某个场景用的补充，不是第二个主干。
   实测：`debugging` 包在四轮加固中从 5.4KB 涨到 12.7KB（主干约 15KB），
   继续加规则的边际收益已经很低——**包越长，读它本身的成本越接近它带来的收益**。
   但 1/2 是**经验值不是最优解**：`debugging` 包在 76% 时反而拿到了本项目最干净的一次正收益（+3.33）。
   所以机检把它做成两级：**>50% 警告**（该看一眼还有没有可删的）、**≥100% 报错**（必须拆或删）。

## 三、三条机检（`.build/check_packs.py` 自动跑）

| 检验 | 通过标准 |
|---|---|
| **删包不塌** | 删掉任意一个包：主干仍能运行、落兜底；其余包不被牵连（没有任何文件引用被删的包）；主干有明确的「包不存在或未特化」条款 |
| **插包不改主干** | 只新增一个包文件即可生效，主干零改动 |
| **正交性** | 每个包的字段 3 必须点名至少 2 个具体 `<id>`；被点名的 id 必须存在；易混对双向至少一侧有明确排除 |

另有一条：**主干无场景名**——`SKILL.md` 各节 grep 不到任何包 id 字面。

## 四、当前状态

| 包 | 状态 |
|---|---|
| `planning` / `writing` / `coding` / `refactor` / `debugging` | **已特化**（覆盖有场景请求 ~80%） |
| `decision` / `research` / `learning` / `review` | **未特化**，走主干通用三档装配 |

未特化的场景不是「没实现」——它按通用规则正常工作，只是没有专属的交付形态与硬约束。
新增一个包**只需加一个文件**，不改主干。
