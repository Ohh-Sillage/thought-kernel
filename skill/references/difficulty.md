# 难度自适应分流

## 为什么需要

实测（Round 1）显示，附加思想的收益高度依赖题目难度：

| 难度 | 裸模型基线 | 附加后提升 | 单轮 token 增幅 | 单位成本收益 |
|---|---|---|---|---|
| 简单 | 19.67 / 20（83% 满分） | +0.33 | +40% | 低 |
| 中等 | 19.88 / 20（88% 满分） | +0.12 | +47% | 最低 |
| 复杂 | 18.70 / 20（60% 满分） | +0.60 | +27% | 高 |

简单与中等题的裸模型表现已接近满分天花板，附加思想能拿到的增量极小，却要付出
40—47% 的 token 成本；复杂题才有真实提升空间，且边际成本反而更低。
因此按难度分流：简单题少附加省成本，复杂题照常附加保收益。

## v1.2.0 的教训：中等档砍过头了

v1.2.0 把中等档的人类侧压到「最多 1 条」。Round 2 重评（168 单元，单评委、逐条核对）显示这个力度是错的：

| 指标 | v1.2.0（中等档 1 条人类侧） |
|---|---|
| 中等档分数 | 对上一版 **−0.58** |
| 复杂档分数 | +0.33 |
| 净额 | **0.00**（收益与代价完全抵消） |

根因具体：`decision` 类任务的检查要点要求「分别给出支持与反对的最强论证」（对应 H6），
同时要求「识别锁定点」（对应 H13）。只准 1 条时模型选了 H13、丢掉 H6，
直接失守必需考点，单题掉 4 分。

**结论：中等档的人类侧上限应为 2 条，而不是 1 条。** 中等题的问题不在于「附加太多」，
而在于「附加的关键项不完整」。

## 难度判定

在场景判定之后执行，三个信号取最先成立者：

1. **显式声明**：用户说「这是个小问题」「简单问一下」→ 简单；「这个问题比较复杂」→ 复杂。
2. **任务结构**：单步可答、单一对象、无外部依赖 → 简单；需要 2—3 步或少量信息整合 → 中等；
   多子问题、需要权衡取舍、有不可逆后果、需要外部信息 → 复杂。
3. **默认**：均无法判定时按中等处理。

难度只看当前这条消息，不继承历史判定。

## 分档附加规则

| 难度 | 人类侧 | 机器侧 | 模板 | 自检 |
|---|---|---|---|---|
| 简单 | 不自动附加 | 1 条（默认 M10 反馈控制） | 短指令 | 输出前 1 次 |
| 中等 | 最多 2 条 | 最多 2 条 | 短指令至标准 | 输出前 1 次 |
| 复杂 | 按模式上限（balanced 3 条） | 按模式上限（balanced 2—3 条） | 标准或完整 | 按模式 |

规则要点：

1. 难度只调「附加多少」，不改附加方式（wrap / interactive / inject 由思想本身决定）。
2. 简单档保留 M10 自检——这是简单题唯一的实质收益来源，不因省 token 而丢弃。
3. 简单档不自动附加人类侧思想，也不输出标注行——省 token 就省到底，用户问起再说明。
4. 用户显式点名的思想不受难度裁剪。
5. 难度裁剪与模式裁剪叠加时，取更严的一档。
6. **结构性必需优先**：裁剪前先判断本场景的默认人类侧思想里哪些对应任务的必需考点
   （如 decision 的 H6 正反论证、planning 的 H4 需求澄清），这些必须优先保留，
   不得因为「只留 1 条」而被随机挤掉。宁可少留一条非必需思想，也不丢必需项。
7. **场景包优先于本表**。若当前场景有场景包，且包内声明了注入额度或「不注入思考框架」，
   以包为准，本表的三档规则对该场景不适用。只有未特化的场景才走本表。
8. **medium 档必须把抽象要求落到该场景可核对的实体上，不得只给条目标题**。
   > **迁移进度（T30 第二批，2026-10-26）**：按场景列的「核对实体」属于**场景知识**，
   > 按三层架构应迁入各自的场景包（字段 6 硬约束）。**已迁走**：`planning` / `writing` / `refactor`
   > （见 `@references/packs/` 对应文件）。**仍在本文**：`learning` / `research` / `decision` / `review` /
   > `exec`——这四个半场景没有专属包，暂留此处作为过渡。迁完后本规则只保留「必须落到可核对实体」这条通用要求。
   实测（2026-10-26）：把 medium 题压到 1200 字符左右、只列条目标题会稳定掉分。
   但「具体」的标准按场景不同，**不能一律理解为「给数字」**：
   - `planning` / `exec`：给具体数值、验收标准、时间窗
     （例：「第 4 周能不看稿讲满 3 分钟，卡顿 ≤3 次」）
     → `planning` 部分**已迁入该场景包**（按场景 id 查 `@references/scenario-map.md` 的包索引）；`exec` 仍用本行
   - `learning`：给生活化类比、常见误区、反例
     （例：「索引像词典的检字表」+ 明确指出「索引越多越好」是错的）
   - `research`：给证据分级、来源类型、结论强度
     （例：「这个说法只有观察性证据支持，撑不起精确数字」）
   - `decision` / `review`：给可验证事实与假设的区分、决策节点
   - `writing`：给**可直接使用的成文成品**（邮件正文、文章正文、报告全文），
     不是大纲、要素清单或「该写什么」的指引；篇幅按体裁定，邮件可以短但不能缺要素；
     用户未提供的具体信息用占位符并标注，不得编造
     → **已迁入该场景包**（按场景 id 查包索引；含「主体占位、其余写实」的细化）
   实测依据：规则里漏掉 writing 时，medium 写作题的配对差是 **−3.33**（超噪声 5 倍）——
   模型把「写邮件」做成了要素清单，用户拿不到能直接发的稿子；
   同题里唯一交出完整成稿的那份得分最高。
   规则 8 其余场景的实测依据：只压成条目标题时，planning / refactor 靠「给数值」修好了（+1.00 / 0.00），
   但 learning 仍掉 1.00——它的核对实体是类比与误区，不是数字。
   **给数字时要区分三类，不要一律占位**：
   - **通用经验阈值**（如「圈复杂度 >15 需拆」「参数 >4 个」「测试覆盖 <60%」）——
     **直接给，不要占位**。这类数字是行业经验值，不是用户的数据，占位反而让人没法直接用；
   - **用户特定数据**（如团队人数、实际 QPS、具体日期、既有代码行数）——
     用 `<占位>（此处替换为真实内容）` 标注；
   - **无来源的量化断言**（如「拆分能降低 3%—8% 开销」）——**不要编**，
     改成定性表述（「通常会多一层调用开销」）或标「需实测」。
   实测依据：refactor 场景里把通用阈值也占了位，导致 usability 全线被扣（三份都是 4，
   而裸模型那份无占位、拿 5），该场景配对差 **−1.50**，是 10 个场景里唯一的负收益；
   同一批里还有一份编了「3%—8%」这种无来源断言，被扣 correctness。
   只写标题而不落到该场景的实体，算未完成。若用户明确要求省 token，
   改走 `@references/special-directions.md` 的 D1 极限压缩。

## 与模式的关系

模式（efficiency / balanced / accuracy）管「形式」：条数、模板长度、场景数、自检强度。
难度管「值不值得附加」：简单题省成本，复杂题保收益。
两者正交，叠加取更严者。

| 用户输入 | 模式 | 难度 | 实际附加 |
|---|---|---|---|
| 简单问答 | balanced | 简单 | 仅 M10，无标注 |
| 简单问答 | efficiency | 简单 | 仅 M10，无标注 |
| 设计方案 | balanced | 复杂 | 人类侧 3 + 机器侧 2—3（完整流程） |
| 设计方案 | accuracy | 复杂 | 人类侧 4 + 机器侧 3—4（完整流程） |

## 已知限制

当前测试集为单轮输入，无法测出 interactive 流程在多轮下的轮数差异。
难度分流对「轮数」的节省效果尚待多轮用例验证。
