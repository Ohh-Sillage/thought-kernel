# 场景映射

## 识别方法

> 词表的**唯一真相源**是 `.build/scenario_spec.json`，下表由 `.build/detect_scenario.py --emit-md` 生成。
> 改词表请改 spec 再重新生成，不要手改表格（`--check-md` 会机检两者是否一致）。

1. **关键词打分**：核心词（下表加粗）权重 2（`要不要`/`该不该` 为 3，它们是无歧义的决策标记），
   普通词权重 1。同一关键词无论出现几次只计一次。
2. **激活判定**：命中权重和 **≥2**，或命中 **1 个非泛词**（泛词 = 「代码」「项目」这类在任何技术文本里
   都出现的词，不能单独构成激活）。**不达线 → 按通用执行处理。**
   本步骤只对**已通过 `SKILL.md` 前置闸门**的请求生效：闸门判「跳过」（零落差）的请求根本不进场景判定。
   因此「不达线」≠「跳过」——前者是认不出场景，后者是没有值得做的事。

   **裸名词短语兜底**：关键词全部未命中、但形态就是「一个短名词短语」时，判 `learning`——
   判据：≤16 字、无标点、无比较/清单类动词（介绍/推荐/区别/优劣/哪些/怎么/如何）、无第一人称与情绪、
   无故障词（报错/崩溃/蓝屏/异常/失败/超时）、**无指令动词与应答词**
   （改/加/删/试/重启/执行/生成/去掉/修改/设置/部署…、继续/可以/好的/行/嗯/已/保留/导出/发送…）。
   剥掉疑问尾（是啥/啥意思/的用处）后，**含拉丁或数字放宽到 2 字，纯中文须 ≥3 字**。
   例：`SDK`、`MLP`、`冷启动`、`召回率`、`lr是啥`、`L1呢`。
   **这类词关键词永远救不了**（里面没有任何问句词），所以按结构判，不要再往词表里加词。
   **必须在两种分布上都验**：DeepSeek 式提问的短句多是术语，harness 式提问的短句多是指令与续接
   （「继续」「试下shell」「p0 p1 p2都修改」）——不加指令词排除，这条规则在 harness 上会净伤害。
3. **排序**：①核心词命中数 ②权重和 ③置信度（权重和 ÷ 该场景总权重）。
   按当前模式的场景数上限取前 N 个。
4. **语义判断（主通路，不是例外）**：真实用户提问往往关键词稀疏。**关键词不达线不代表意图不明**——
   按任务意图归类，例如「这个报错咋整啊一直起不来」意图属于 `debugging`，
   「帮我看看这个方案还有啥问题」属于 `planning`。
   关键词只负责高置信度的快路径，其余靠语义。
5. **多场景命中**：按第 3 步排序取前 N 个（`efficiency` 取 top-1，`balanced` / `accuracy` 取 top-2）。
6. **阶段续接（可执行版）**：当前句**不激活任何场景**时，不要凭感觉拼上文，按三步走。

   **① 这句话算不算「靠上文才有意义」的续接？** 只有这几种形态算——
   - **补附件 / 贴长文本**：以 `@image#` / `@file#` / `@scene#` / `@long-text` 等标记开头
   - **短句（≤20 字）**：含续接词（继续 / 下一步 / 可以 / 好了 / 执行 / 第 N 步 / 完成了…），
     或**以指代词开头**（这 / 那 / 它 / 上面 / 前面 / 刚才）
   - **中短句（21—60 字）**：同上
   - **长文本（>60 字）且是「贴素材」形态**：≥2 行以编号 / 表格 / 列表开头，
     或 >100 字且含 ≥3 处 `**`

   **不算续接的**（宁可判不出，也不要继承）——
   - `为什么导入zip包技能失败`（12 字但是个完整问题，只是词表没识别出来）
   - `…卡住这个问题帮我记入个人知识库…`（87 字，自足请求）
   - `标价` / `取图`（2 字，没有续接词也没有指代词——判不出就是判不出）

   **② 往回找最近一个能识别出场景的轮次，不是只看上一轮。** 上一轮本身可能也是「继续」。
   最多回溯 5 轮。找到就用它的场景；5 轮内都识别不出，再按兜底处理。

   **③ 不许用继承覆盖已有判定。** 当前句自己激活了场景就用它自己的；继承只在「完全不激活」时生效。

   **实测代价**（2026-10-26，225 条真实标注）：31 条「判不了」里救回 **18 条（58%）**，
   而可达上界是 20 条（另外 8 条的上文识别不出，3 条无上文）——可达范围内达成率 **90%**。
   代价是 66 条「不属于」里误继承 **8 条（12%**，低于 15% 门槛）。
   **把「短」本身当续接信号是坏交易**：只多救 2 条，却新增 19 条误激活——
   短句的自足性不低，必须有续接信号才算。

**为什么废掉旧的「置信度 <0.4」**：旧公式把阈值定在「命中权重和 ÷ 总权重 ≥ 0.4」，
需要同时命中 3—4 个词。实测现有 64 道题**没有一道能达到**（单核心词命中只有 0.14—0.25），
而实测又有明显效果——说明模型实际走的是第 4 步语义判断，公式形同虚设。
现在改成「权重和 ≥2」这类可执行、可验证的规则，并配 `.build/detect_scenario.py` 量化判定正确率。

场景判定完成之后，**按本表取该场景的场景包**。包内定义「交付形态 / 注入内容 / 硬约束 / 自检项」，
优先级高于本文件的映射表与 `@references/difficulty.md` 的三档附加表。

**包缺失或未特化时的行为**（这条是「删包不塌」的保证）：按通用三档装配正常作答，不报错、不失真、
不因为「找不到专项规则」而把答案缩短或改成反问。未特化 ≠ 没实现。

前五个场景（planning / writing / coding / refactor / debugging）合计覆盖投放平台有场景请求的约 **80%**，
已全部特化。`decision` / `research` / `learning` / `review` 仍走通用三档——这是有意的，不是欠账：
它们在投放平台上的份额合计不到 10%，先特化收益低于维护成本。

新增或修改场景包前必读 `@references/packs/_contract.md`（8 字段 + 四个「不许」+ 三条机检 + 体量上限）。

## 合并规则

1. 用户显式点名的思想与场景默认思想取并集。
2. 按 id 去重；同一 id 只注入一次。
3. 排序：`wrap` 在前，`interactive` 次之，`inject` 最后（`inject` 不进入正文）。
4. 人类侧默认思想属于建议，需按 `modes.md` 的确认策略处理：`balanced` 与 `accuracy` 弹建议卡片，`efficiency` 既不弹卡片也不输出标注。
5. 裁剪顺序：先按模式上限裁机器侧，再裁人类侧，最后裁场景数。裁掉时不解释。
6. 用户点名思想不受裁剪影响。

## 冲突处理

- 同一输入命中多个场景且人类侧建议重复（如 learning 与 writing 都含 H1）：并集去重后保留一次。
- 场景默认思想落在失效边界内（如 decision 场景的 M3）：跳过该思想，不替换为同类。
- 用户点名的思想与场景默认完全重合：只注入一次，标注（用户索要时）不重复列出。
